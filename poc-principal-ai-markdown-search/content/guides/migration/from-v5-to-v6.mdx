# Migrating from <VersionToolLink of={current.oswald.version}/> to <VersionToolLink of={next.oswald.version}/>
Released in <VersionToolLink of={next.oswald.release}/>.

## Highlights
Oswald <VersionToolLink of={next.oswald.version}/> focuses on updating the build stack, removing deprecated features, renaming all packages and bumping other tools and dependencies to more recent versions.

- **Engines**: _Most notable changes_
  <VersionToolHighlightList of={next.engines} />
- **Tools and dependencies**: _Most notable changes_
  <VersionToolHighlightList of={next.dependencies} />
- **Features** 🎉
  - Bundling with [`vite`](https://vitejs.dev) instead of [`webpack`](https://webpack.js.org)
    - Faster
    - More reliable
    - Better TypeScript support
    - Same code for `dev` and `production` modes
    - ESM support
    - HMR support
  - Testing with [`vitest`](https://vitest.dev) instead of [`jest`](https://jestjs.io)
    - Leverages the same `vite` configuration to transpile code before testing
    - No configuration required when using `oswald test`
    - ESM support
  - [`oswald`](../../cli/oswald.md) cli, aggregating all clis in one place
  - [`oswald application`](../../cli/oswald-application.md) cli for managing application bundling
  - [`oswald codemod`](../../cli/oswald-codemod.md) cli for managing code migration
  - [`oswald configuration`](../../cli/oswald-configuration.md) cli for managing configuration
  - [`oswald editor`](../../cli/oswald-editor.md) cli for managing the editor
  - [`oswald expressions`](../../cli/oswald-expressions.md) cli for managing expressions kept in external providers
  - [`oswald test`](../../cli/oswald-test.md) cli for managing unit testing
- **Moved, removed, renamed or replaced**
  - We took this opportunity to **reorganize and rename** our packages
  - We removed deprecated components and functions
  - We renamed/rewritten inconsistent components and functions

## Migration steps

### 1. Prepare
<Admonition type="tip">
  We recommend updating your project to the latest <VersionToolLink of={current.oswald.version}/> before upgrading to <VersionToolLink of={next.oswald.version}/>.
</Admonition>

<Admonition type="danger">
  The editor will crash if you try to open a fragment that uses a component that doesn't exist.
  For that reason, you need to migrate away from the components that were removed in <VersionToolLink of={next.oswald.version}/> while still using <VersionToolLink of={current.oswald.version}/>.
  If you migrate to <VersionToolLink of={next.oswald.version}/> while still using those components, you won't be able to use the editor to remove them.

  Check the [Breaking changes](#breaking-changes) section to find the components and migrate away from them **before migrating to <VersionToolLink of={next.oswald.version}/>**.
</Admonition>

### 2. Required tools
Oswald <VersionToolLink of={next.oswald.version}/> requires the following:
  <VersionToolRequirementList of={next.engines} />

### 3. Required access
Oswald's packages are now available on GitHub Packages under the `@philips-internal` organization and do not require any VPN connection to be installed.
However, GitHub Packages require authentication. Follow the guide below to get or validate your access.

#### 3.1 Configure authentication to GitHub packages
> See: [GitHub packages authentication](../../guides/github-packages-authentication.mdx)

<Admonition type="danger">
  If you have a `@philips-emr` scoped registry (or an unscoped registry) in your `.npmrc`, **DO NOT** remove it yet.
  You should only remove it after finishing the migration on this guide.
  If you remove it right now, your current `@philips-emr/tws-*` dependencies will generate an error when you try to install.

  <Admonition type="tip">
    Don't forget to remove it after.
  </Admonition>
</Admonition>

#### 3.2 Test your access
Running the following command in your terminal should output the package version, without errors.

```shell
npx --package @philips-internal/oswald -- oswald --version
```

### 4. Run the codemods
Codemods are automated scripts that attempt to do most of the work of renaming and/or refactoring the necessary things.

**Run them all.**

<Admonition type="important">
  They are made to be run in your **project's root directory** only.
</Admonition>

<Admonition type="note">
  - If you want to try any of the codemods without changing any files, add `--dry` to the command.
  - If you want more details about the execution (like the exact file paths), add `--verbose` to the command.
  > The flags can be used simultaneously.
</Admonition>

- Renames oswald packages within imports
  ```shell
  npx --package @philips-internal/oswald -- oswald codemod run v6-rename-code-imports-from-tws-to-oswald
  ```

- Renames `Fragment` to `FragmentReference` in `*.osw` files
  ```shell
  npx --package @philips-internal/oswald -- oswald codemod run v6-rename-osw-fragment-references
  ```

- Renames oswald dependencies in `package.json` files
  ```shell
  npx --package @philips-internal/oswald -- oswald codemod run v6-rename-package-dependencies-from-tws-to-oswald
  ```

- Renames oswald cli commands in `package.json` files
  ```shell
  npx --package @philips-internal/oswald -- oswald codemod run v6-rename-package-scripts-from-tws-to-oswald
  ```

- Renames oswald dependencies in `.oswaldrc.json` files
  ```shell
  npx --package @philips-internal/oswald -- oswald codemod run v6-rename-runtime-dependencies-from-tws-to-oswald
  ```

### 5. Dependencies
This will help you migrate to <VersionToolLink of={next.oswald.version}/>.

<Admonition type="caution">
  Goes without saying, but don't change anything under any `node_modules` directory.
</Admonition>

#### 5.1 Verify TWS dependencies
Make sure there are no TWS dependencies (the [codemods](#4-run-the-codemods) should have removed them all) by searching for any `@philips-emr/tws-` within `package.json` files across your entire project.
If you find any, rename it to the corresponding Oswald dependency using the list under the `Renamed` section of the [Breaking changes](#breaking-changes).

#### 5.2 Verify Oswald dependencies
Make sure there are no Oswald dependencies (the [codemods](#4-run-the-codemods) should have added them all) with a different version by searching for any `@philips-internal/oswald-` within `package.json` files across your entire project.
If any of them are a different version, change it to the same version as the others.

#### 5.3 Bump other dependencies
Search for each dependency listed below in all of your `package.json` files and update them all to the same exact specified version, so there are no conflicting versions to cause problems.
**Ignore the ones you do not depend on and do not add them either.** The necessary ones come included in Oswald.

<VersionToolInstructionsList of={next.instructions.bump}/>

<Admonition type="danger">
  ***DO NOT ADD*** any of these dependencies if you don't ***REALLY*** need to use them directly.
</Admonition>

<Admonition type="tip">
  You can (and probably should) remove the ones you do not use directly (i.e. is not imported anywhere in your code).
  Except for `typescript`, which is usually not imported in code.
</Admonition>

#### 5.4 Remove other dependencies
Search for each dependency listed below in all of your `package.json` files and remove them all.
This will help avoid conflicts, as these dependencies either have been replaced by others, or you should not be using them directly.

<VersionToolInstructionsList of={next.instructions.remove}/>

#### 5.5 Reset
This will ensure a fresh dependencies tree, without conflicts, dupes or leftovers from previous versions.
```shell
npx rimraf --glob '**/node_modules' '**/package-lock.json'
```

#### 5.6 Install
Run the following command to install everything.
```shell
npm install
```

### 7. Modify Oswald's CLI uses
Most of the usages of the old CLI should have been changed in the [3.3 Run the codemods](#41-run-the-codemods) section of this guide.
However, **the codemods do NOT handle CLI arguments**, so you'll need to check the scripts that have changed in all of your `package.json` files and migrate the arguments as described below.

#### `tws-editor`
Replaced by [`oswald editor run`](../../cli/oswald-editor.md#oswald-editor-run) and [`oswald editor watch`](../../cli/oswald-editor.md#oswald-editor-watch) cli commands.
Both the previous and the new commands do not accept arguments, so **no change should be necessary**.

#### `tws-expressions`
Replaced by [`oswald expressions`](../../cli/oswald-expressions.md) cli commands.
No arguments have been changed, so **no change should be necessary**.

#### `tws-builder`
Replaced by [`oswald application build`](../../cli/oswald-application.md#oswald-application-build) and [`oswald application dev`](../../cli/oswald-application.md#oswald-application-dev) cli commands.
All previous arguments have been removed and are now configured through the `application` and `builder` sections of the `.oswaldrc.json` configuration file.
  - `--context-name` is now `application.context`
  - `--entry` is now automatic and **NOT** necessary anymore
  - `--mode` is now automatic and **NOT** necessary anymore
  - `--output` is now `builder.directory`
  - `--output-war` is now `--archive` + `builder.archive.directory` and `builder.archive.name`
  - `--output-war-web-inf` is now `builder.archive.include`
  - `--tsconfig` is now automatic and **NOT** necessary anymore

<Admonition type="note" title="About archiving">
  Although archiving is now configured through `builder.archive` in `.oswaldrc.json`, the file will only be generated when the `--archive` flag is supplied to the `oswald application build` command.
  The other commands under the `oswald application` cli will ignore this flag.
</Admonition>

<Details summary={<summary>Example: build into <code>./dist</code> without war or context</summary>}>
  From:
  ```shell
  tws-builder bundle \
    --mode production \
    --entry lib\index.js \
    --output dist \
    --tsconfig tsconfig.json
  ```

  To:
  ```shell
  oswald application build
  ```

  <Admonition type="note">
    For this command, no configuration is necessary in `.oswaldrc.json`
  </Admonition>
</Details>

<Details summary={<summary>Example: build into <code>./dist</code> and <code>./ROOT.war</code>, without context</summary>}>
  From:
  ```shell
  tws-builder bundle \
    --mode production \
    --entry lib\index.js \
    --output dist \
    --output-war ROOT \
    --output-war-web-inf war/WEB-INF \
    --tsconfig tsconfig.json
  ```

  To:
  ```shell
  oswald application build --archive
  ```

  With:
  ```json5 title=".oswaldrc.json"
  {
    "$schema": "node_modules/@philips-internal/oswald-tooling-configuration/schemas/runtime.json",
    "builder": {
      "archive": {
        "directory": ".", // project directory
        "name": "ROOT", // will generate ROOT.war
      },
    },
  }
  ```
</Details>

<Details summary={<summary>Example: build into <code>./output</code> and <code>./context.war</code>, with context <code>/context</code></summary>}>
  From:
  ```shell
  tws-builder bundle \
    --context my-context \
    --mode production \
    --entry lib\index.js \
    --output my-output \
    --output-war my-context \
    --output-war-web-inf war/WEB-INF \
    --tsconfig tsconfig.json
  ```

  To:
  ```shell
  oswald application build --archive
  ```

  With:
  ```json5 title=".oswaldrc.json"
  {
    "$schema": "node_modules/@philips-internal/oswald-tooling-configuration/schemas/runtime.json",
    "application": {
      "context": "/context", // optional
    },
    "builder": {
      "archive": {
        "directory": ".", // project directory
        "name": "context", // will generate context.war
        "include": {
          "war": ".", // copies contents of war into root
          // or
          "war/WEB-INF": "WEB-INF", // copies contents of war/WEB-INF into WEB-INF
        },
      },
      "directory": "output", // optional, defaults to dist
    },
  }
  ```
</Details>

### 8. Modify TypeScript's configuration

  - Add `ES2021` to `compilerOptions.lib`
  - Change `compilerOptions.module` to `ES2022`
  - Change `compilerOptions.target` to `ES2021`
  - Change `useDefineForClassFields` to `false`

```json5
    // diff-add-next-line

  }
}
```

### 10. `HTML` file
The `HTML` file is now the entry point of your application, not a script file like it was before.
  1. **Move it**: Move `HTML` file to the same directory as the `.oswaldrc.json` configuration file.
  2. **Rename it**: This file should be named `index.html`.
  3. **Add the main script to it**: Load the main script into the `HTML` file, following this example:
      ```html
      <!DOCTYPE html>
      <html lang="en">
        <head>
          <!-- ... -->
        </head>
        <body>
          <noscript>You need to enable JavaScript to run this app.</noscript>
          <div id="root"></div>
          <!-- diff-add-next-line -->
          <script type="module" src="/src/index.tsx"></script>
        </body>
      </html>
      ```

<Admonition type="danger">
  If your `HTML` file is not found in the right place with the right name, the build will fail.
</Admonition>

### 11. `SASS`/`SCSS` files
Oswald no longer supports `SASS`. Therefore, it is necessary to migrate all `SASS` files to pure `CSS` files.

#### 11.1 File extensions
All files with `.scss` and/or `.sass` extensions should be changed to use the `.css` extension.

#### 11.2 Variables
One of the main differences between `SASS` and `CSS` is the variables' syntax.

> See:
>  - [SASS variables](https://sass-lang.com/documentation/variables)
>  - [Using CSS custom properties (variables)](https://developer.mozilla.org/en-US/docs/Web/CSS/Using_CSS_custom_properties)
>  - [Custom properties (--*): CSS variables](https://developer.mozilla.org/en-US/docs/Web/CSS/--*)

All variables starting with `$` need to be replaced, following this example:

<table style={{ display: 'inline-table', width: '100%' }}>
  <thead>
    <tr>
      <th style={{ width: '50%', textAlign: 'left' }}>`.scss`</th>
      <th style={{ width: '50%', textAlign: 'left' }}>`.css`</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>
        ```scss
        .classname {
          border-color: $safety-red;
          color: $white;
        }
        ```
      </td>
      <td>
        ```css
        .classname {
          border-color: hsl(var(--color-safety-red));
          color: hsl(var(--color-white));
        }
        ```
      </td>
    </tr>
  </tbody>
</table>

<Admonition type="note">
  The variable `--color-white` has a `Hue-Saturation-Lightness` value of: `0, 0%, 100%`

  | Function | Description |
  | -- | -- |
  | [`hsl()`](https://www.w3schools.com/cssref/func_hsl.asp) | Defines colors using the `Hue-Saturation-Lightness` model |
  | [`hsla()`](https://www.w3schools.com/cssref/func_hsla.asp) | Defines colors using the `Hue-Saturation-Lightness-Alpha` model |

  > For more color variables check: https://github.com/philips-internal/oswald/tree/main/packages/theme/css/theme
</Admonition>

#### 11.3 Property declarations
`SASS` provides a number of syntax features that are not supported by standard `CSS`, such as interpolation, nesting, hidden declarations, custom properties, parent selectors and placeholder selectors.
Instead of repeating explanations and examples, we'll point to the `SASS` documentation, where you can see examples of how to migrate to `CSS`.

Links:
  - [Interpolation](https://sass-lang.com/documentation/style-rules/declarations#interpolation)
  - [Nesting](https://sass-lang.com/documentation/style-rules/declarations#nesting)
  - [Hidden declarations](https://sass-lang.com/documentation/style-rules/declarations#hidden-declarations)
  - [Custom properties](https://sass-lang.com/documentation/style-rules/declarations#custom-properties)
  - [Parent selectors](https://sass-lang.com/documentation/style-rules/parent-selector)
  - [Placeholder selectors](https://sass-lang.com/documentation/style-rules/placeholder-selectors)

### 12. React `v18`
React `v18` changed the way the root node should be rendered. Change your `index.tsx` accordingly.

```tsx
import React from 'react';
import type { ReactElement } from 'react';
// diff-remove-next-line
import ReactDOM from 'react-dom';
// diff-add-next-line
import { createRoot } from 'react-dom/client';

import '@philips-emr/tws-components';
import { Foundation } from '@philips-emr/tws-foundation';

import { bootstrap } from './configuration';

function RootApp(): ReactElement {
  return (
    <Foundation
      bootstrap={bootstrap}
      root={{
        fragmentName: 'root',
      }}
    />
  );
}

// diff-remove-next-line
ReactDOM.render(<RootApp />, document.getElementById('root'));
// diff-add-start
const container = document.getElementById('root');

if (container) {
  const root = createRoot(container);
  root.render(<RootApp />);
}
// diff-add-end
```

## Other notable changes
This section adds details about some changes mentioned in the [Breaking changes](#breaking-changes) section and how to migrate them.

### `ConfigurationService`

#### `endpointMappers` replaced
The `setAuthenticationConfiguration` method was changed as to not be necessary to pass the `endpointMappers` property, giving this responsability to a new method, called `setEndpointMappers`, following the same signature.

```tsx
import { ConfigurationService } from '@philips-internal/oswald-ui-core/lib/services';

function setupAuthentication(): void {
  ConfigurationService.setAuthenticationConfiguration({
    clientId: 'example',
    // diff-remove-start
    endpointMappers: {
      information: informationMapper,
    },
    // diff-remove-end
    endpoints: {
      ...
    }
  });

  // diff-add-start
  ConfigurationService.setEndpointMappers({
    information: informationMapper,
  });
  // diff-add-end
}
```

### `AuthenticationService`

#### Manual token restoration required
When routes are not configured through the editor authentication manager, you must manually call `await AuthenticationService.restoreTokenFromStorage();` to restore the session from browser storage.

```tsx
import { AuthenticationService } from '@philips-internal/oswald-ui-core/lib/services';

async function loadAuthentication(): Promise<void> {
  // Set up your authentication configuration
  ConfigurationService.setAuthenticationConfiguration({
    clientId: 'your-client-id',
    endpoints: {
      // ... your endpoints
    },
    routes: {
      // ... your routes
    },
    // ... other configuration
  });

  // Manually restore token from storage
  await AuthenticationService.restoreTokenFromStorage();
}
```

<Admonition type="note">
  When using the editor authentication manager, this call is automatically handled by the foundation's authentication loading process.
</Admonition>

### `HttpService`
The request options no longer support the properties described below. If you use any of them, you'll probably need to migrate the code (check the examples).

<Admonition type="note">
  Some types have been renamed, check the [Breaking changes](#breaking-changes) section.
</Admonition>

#### `requestBodyMapperType` removed
Instead of using `requestBodyMapperType`, the body should be provided in the correct type and the service will map it automatically.  
The request body accepts these types:
  - `Blob`
  - `FormData`
  - `Record<string, Value>`
  - `string`
  - `URLSearchParams`

<Details open summary={<summary>Example: <code>Blob</code> request</summary>}>
  From:
  ```tsx
  const url = '...';
  const parameters = {};

  HttpService.post(url, parameters, {
    requestBodyMapperType: RequestBodyMapperType.BLOB,
    body: {
      file,
    },
  });
  ```

  To:
  ```tsx
  const url = '...';
  const parameters = {};

  const formData = new FormData();
  formData.append('file', file, file.name);

  HttpService.post(url, parameters, {
    body: formData,
  });
  ```
</Details>

#### `responseBodyMapperType` removed
Instead of using `responseBodyMapperType`, the `Content-Type` provided by the server's response will be used to map the body to the final result.  
Built-in mapping:
  - Mapped to `T`
    - `application/json`
  - Mapped to `Blob`
    - `application/octet-stream`
    - `image-bmp`
    - `image-gif`
    - `image-jpeg`
    - `image-png`
  - Mapped to `string`
    - `text/css`
    - `text/html`
    - `text/plain`

<Details open summary={<summary>Example: <code>Blob</code> response</summary>}>
  From:
  ```tsx
  const url = '...';
  const parameters = {};

  HttpService.get<Blob>(url, parameters, {
    responseBodyMapperType: ResponseBodyMapperType.BLOB,
  });
  ```

  To:
  ```tsx
  const url = '...';
  const parameters = {};

  HttpService.get<Blob>(url, parameters);
  ```
</Details>
