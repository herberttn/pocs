# Migrating from <VersionToolLink of={current.oswald.version}/> to <VersionToolLink of={next.oswald.version}/>
Released in <VersionToolLink of={next.oswald.release}/>.

## Highlights
Oswald <VersionToolLink of={next.oswald.version}/> focuses on removing deprecated features and bumping other tools and dependencies to more recent versions.

- **Engines**: _Most notable changes_
  <VersionToolHighlightList of={next.engines} />
- **Tools and dependencies**: _Most notable changes_
  <VersionToolHighlightList of={next.dependencies} />
- **Moved, removed, renamed or replaced**
  - We took this opportunity to **reorganize and rename** some things within our packages
  - We removed deprecated components and functions
  - We renamed/rewritten inconsistent components and functions

## Breaking changes

- **Engines**
  <VersionToolHistoryList from={current.engines} to={next.engines} />
- **Tools and dependencies**
  <VersionToolHistoryList from={current.dependencies} to={next.dependencies} />
- **Changed**: _Things that don't necessarily fit in the other categories_
  - Command line option `--reports` renamed to `--reporters` for the following commands:
    - [`oswald application build`](../../cli/oswald-application.md#oswald-application-build)
    - [`oswald library build`](../../cli/oswald-library.md#oswald-library-build)
  - Component `Login` now only renders the children if they have a slot defined
  - Function `updateChildValidations` from `FieldContext` now only accepts a promise returning the validations
  - [Methods of components, APIs and interfaces now return a promise:](#components-apis)
    - `DetailAPI.isValid`
    - `DetailAPI.submit`
    - `DetailAPI.validate`
    - `FieldAPI.isValid`
    - `FieldAPI.validate`
    - `FormAPI.isValid`
    - `FormAPI.submit`
    - `FormAPI.validate`
    - `Validatable.isValid`
    - `Validatable.validate`
  - [Service `ModelService` now only accept registering async validators](#modelservice)
  - [Service `ValidationRunner` now runs asynchronously](#validationrunner)
- **Moved**: _Things that moved location_
  - from `@philips-internal/oswald-ui-constants` to `@philips-internal/oswald-ui-components`
    - [`ThemeColor`](#services-that-moved)
    - [`ThemeTonalRange`](#services-that-moved)
  - from `@philips-internal/oswald-ui-core` to `@philips-internal/oswald-ui-components`

  - Property `AboutBox.versionDate`
  - Property `FieldSet.collapsible`
  - Property `FieldSet.title`
  - Property `Login.localizedLabel`
  - Function `LoginAPI.getLocalizedLabel`
  - Function `LoginAPI.setLocalizedLabel`
  - Option `ButtonTheme.DEFAULT`
- **Renamed or replaced**: _Things that were just renamed or replaced (rewritten) and now have improved equivalents_
  - Second parameter of method `requestClose` from interface `BrowsingContextServiceInterface` changed from string parameter to object parameter with type `BrowsingContextRequestCloseOptions`

## Migration steps

### 1. Prepare
<Admonition type="tip">
  We recommend updating your project to the latest <VersionToolLink of={current.oswald.version}/> before upgrading to <VersionToolLink of={next.oswald.version}/>.
</Admonition>

### 2. Required tools
Oswald <VersionToolLink of={next.oswald.version}/> requires the following:
  <VersionToolRequirementList of={next.engines} />

### 3. Dependencies
This will help you migrate to <VersionToolLink of={next.oswald.version}/>.

<Admonition type="caution">
  Goes without saying, but don't change anything under any `node_modules` directory.
</Admonition>

#### 3.1 Bump Oswald dependencies
Bump all occurrences of all Oswald dependencies to the same <VersionToolLink of={next.oswald.version}/> version.

Make sure there are no Oswald dependencies with a different version by searching for any `@philips-internal/oswald-` within `package.json` files across your entire project.
If any of them are a different version, change it to the same version as the others.

#### 3.2 Bump other dependencies
Search for each dependency listed below in all of your `package.json` files and update them all to the same exact specified version, so there are no conflicting versions to cause problems.
**Ignore the ones you do not depend on and do not add them either.** The necessary ones come included in Oswald.

<VersionToolInstructionsList of={next.instructions.bump}/>

<Admonition type="danger">
  ***DO NOT ADD*** any of these dependencies if you don't ***REALLY*** need to use them directly.
</Admonition>

<Admonition type="tip">
  You can (and probably should) remove the ones you do not use directly (i.e. is not imported anywhere in your code).
  Except for `typescript`, which is usually not imported in code.
</Admonition>

#### 3.3 Remove other dependencies
Search for each dependency listed below in all of your `package.json` files and remove them all.
This will help avoid conflicts, as these dependencies either have been replaced by others, or you should not be using them directly.

> Yes, we are repeating dependencies from previous migration guides in this list because you should **check again** if you have any of them in your project and remove them all if you do.

<VersionToolInstructionsList of={next.instructions.remove}/>

#### 3.4 Reset
This will ensure a fresh dependencies tree, without conflicts, dupes or leftovers from previous versions.
```shell
npx rimraf --glob '**/node_modules' '**/package-lock.json'
```

#### 3.5 Install
Run the following command to install everything.
```shell
npm install
```

### 4. Build and fix
Most of the changes necessary are done at this point.  
Now it's a matter of building your TypeScript project and fixing the remaining problems.  
Use the [Breaking changes](#breaking-changes) section to search for the relevant class, function, service or type and find what has changed.  

**Rinse and repeat.**

### 5. Start and test
Start your application by using your `npm` task that executes the [`oswald application dev`](../../cli/oswald-application.md#oswald-application-dev) cli command.  
Then, test your application to make sure everything is working as it was before.

## Other notable changes
This section adds details about some changes mentioned in the [Breaking changes](#breaking-changes) section and how to migrate them.

### Async validators
The `ModelService` and the `ValidationRunner` have been modified to support asynchronous validators.

#### `ModelService`
The service now only accepts async validators in the `ModelService.registerValidator` method.
If your validator is not async, simply declaring the functions as async will suffice:

<Details summary={<summary>Example: Registering a validator</summary>}>
  From:
  ```tsx
  function customValidator(value: Value): Validation[] {
    const valid = Boolean(value);

    return [{
      message: valid ? '' : 'custom-validator.message',
      name: 'customValidator',
      valid,
    }];
  }

  ModelService.registerValidator(CUSTOM_VALIDATOR, customValidator);
  ```

  To:
  ```tsx
  async function customValidator(value: Value): Promise<Validation[]> {
    const valid = Boolean(value);

    return [{
      message: valid ? '' : 'custom-validator.message',
      name: 'customValidator',
      valid,
    }];

  }

  ModelService.registerValidator(CUSTOM_VALIDATOR, customValidator);
  ```
</Details>

#### `ValidationRunner`
To support the async validators registered in the `ModelService`, the `run` method now returns a promise, update your code to await the validation result:

<Details summary={<summary>Example: Running a validation</summary>}>
  From:
  ```tsx
  const validationRunner = ModelService.validate(value);
  validationRunner.apply(validators.PHONE_NUMBER);

  const validations = validationRunner.run();
  const isValid = validations.every(validation => validation.valid);
  ```

  To:
  ```tsx
  const validationRunner = ModelService.validate(value);
  validationRunner.apply(validators.PHONE_NUMBER);

  const validations = await validationRunner.run();
  const isValid = validations.every(validation => validation.valid);
  ```
</Details>

### Components APIs
API methods, whether directly or indirectly related to validations, now also return a promise.
If your code uses any of the methods mentioned in the [Breaking changes](#breaking-changes) section, update it to await the promise resolution:

<Details summary={<summary>Example: Using a validation API method</summary>}>
  From:
  ```tsx
  @Controller({ fragment: FragmentNames.FRAGMENT })
  export default class FooController {
    @Inject(Aliases.FORM)
    declare form: FormAPI;

    @OnClick(Aliases.BUTTON)
    onButtonClick(): void {
      const valid = this.form.validate();
      // ...
    }
  }
  ```

  To:
  ```tsx
  @Controller({ fragment: FragmentNames.FRAGMENT })
  export default class FooController {
    @Inject(Aliases.FORM)
    declare form: FormAPI;

    @OnClick(Aliases.BUTTON)
    async onButtonClick(): Promise<void> {
      const valid = await this.form.validate();
      // ...
    }
  }
  ```
</Details>
